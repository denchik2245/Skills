# Типографика, переменные и композиция

Правила перенесены из `4-landing/references/layout-system.md` и `knowledge-base.md` и обобщены на страницы и экраны. Конкретная дизайн-система проекта имеет приоритет над стартовыми значениями.

## Цветовая система

Переиспользуй существующие коллекции и семантику. Если их нет, достаточно одной коллекции с именем проекта и одного режима; не создавай примитивы, алиасы и темы, которые сейчас не нужны.

| Группа | Примеры ролей — создавать по необходимости |
| --- | --- |
| `Brand` | `Primary`, `PrimaryHover`, `Soft` |
| `Surface` | `Canvas`, `Default`, `Muted`, `Inverse` |
| `Text` | `Primary`, `Secondary`, `OnInverse`, `OnBrand` |
| `Border` | `Default`, `Strong`, `OnInverse` |

Имя коллекции — `<Проект>`, имя переменной — например `Text/Primary`. Если в файле другая система, продолжай её. Ошибки, успех, фокус и другие роли добавляй только для нужных состояний.

- Одинаковое значение и одинаковая роль — одна переменная. Одинаковый RGB у разных семантических ролей допустим: они могут разойтись в другой теме. Сравнивай коллекцию, режимы, смысл и тип, а не только hex.
- При существующей двухуровневой системе semantic → primitive сохраняй алиасы. Не плодить копии импортированных токенов.
- Для каждой новой переменной явно задавай подходящие `scopes`: `TEXT_FILL`, `FRAME_FILL`, `SHAPE_FILL`, `STROKE_COLOR`, `EFFECT_COLOR` и другие поддерживаемые области. Не оставляй `ALL_SCOPES` без необходимости.
- В многорежимной коллекции заполни все нужные значения. Проверяй активный режим экрана, алиасы и совместимость импортированных переменных; не создавай отдельные `Dark/...` стили ради темы.
- У градиента связываются цвета стопов, у тени — цвет эффекта. Проверь поддержку этих полей в актуальном MCP. Фактические ограничения зафиксируй, а не заменяй привязки совпадающими вручную цветами.
- Контраст проверяй по реально разрешённым значениям активной темы, включая непрозрачность. Не исправляй контраст добавлением случайного локального цвета.

## Текстовые стили

Шрифт бери из существующего файла, брендбука или референса. Если точного шрифта нет, найди ближайший доступный и сообщи замену. При самостоятельном выборе нового шрифта не предлагай Unbounded и Manrope — предпочтение из исходного скилла; существующий брендовый шрифт не заменяй по этому основанию.

Именование и стартовая шкала из `4-landing`:

| Новый стиль | Размер / интерлиньяж, px |
| --- | --- |
| `<Проект>/Display/H1` | 64 / 72 |
| `<Проект>/Heading/H2` | 44 / 52 |
| `<Проект>/Heading/H3` | 24 / 32 |
| `<Проект>/Heading/H4` | 20 / 28 |
| `<Проект>/Numbers/Stat` | 48 / 56 |
| `<Проект>/Numbers/Price` | 24 / 32 |
| `<Проект>/Body/Lead` | 20 / 32 |
| `<Проект>/Body/L` | 20 / 28 |
| `<Проект>/Body/Base` | 16 / 24 |
| `<Проект>/Body/Small` | 12–14 / 20 |
| `<Проект>/Label/Badge` | 12–14 / 20 |
| `<Проект>/Label/Button` | 16 / 24 |
| `<Проект>/Display/Wordmark` | 160 / 160 — только при необходимости |

Это отправная точка для широкого веб-макета, не обязательные размеры интерфейса приложения. Для мобильных экранов, таблиц и плотных рабочих интерфейсов подбери подходящую шкалу, сохрани роли и используй её последовательно. Создавай только используемые стили. Семейство, начертание, размер, интерлиньяж, трекинг и регистр входят в стиль; цвет — в переменную.

- Кегли и интерлиньяжи целые, по возможности кратны 4. Значения 14/20 и 18/28 допустимы; не ломай существующую систему ради кратности.
- Капс задавай через `textCase` текстового стиля, не переписывай исходный текст заглавными. Регистр заголовков выбирай по проекту, не делай все H1 капсом автоматически.
- Не создавай `Body/BaseCopy`, `H2New` и другие дубли. Сначала сравни фактические свойства, затем переиспользуй стиль. Разные цвета и выравнивание текста обычно не требуют нового типографического стиля.
- Смешанный текст проверяй по диапазонам. Для осмысленного другого начертания используй существующий подходящий стиль или один необходимый дополнительный. Не разрывай смысловой абзац на десятки слоёв ради раскраски.
- В русских текстах не оставляй висячих коротких предлогов, союзов и частиц. Неразрывным пробелом соединяй их со следующим словом, тире с предыдущим, число с единицей. Используй `nb()` из [text.js](../scripts/text.js). Не меняй URL, код, артикулы и технические строки; избегай склейки слишком длинных цепочек на узком экране.
- В уже оформленном смешанном тексте меняй только нужные пробелы по диапазонам, предварительно загрузив шрифты; не присваивай весь `characters` заново с потерей форматирования и свойств компонента.
- После смены шрифта, ширины или содержимого перемеряй текст; проверяй центрирование и высоту секции. Кнопки и короткие цены не должны переноситься случайно.
- Основной длинный текст выравнивай влево; колонка мелкого текста — до 800 px, на узких экранах — по доступной ширине. Следи за последней короткой строкой и обрезанием.
- У списков согласуй маркеры, отступы и положение первой строки. В адресе литера дома заглавная: «д. 12Б». Ссылочное подчёркивание и декор визуально различаются.
- По умолчанию не добавляй декоративные надзаголовки-теги над основным заголовком. Сохраняй нужные подписи, хлебные крошки и метки состояния существующего интерфейса.

## Геометрия и композиция

- Границы основных блоков привязывай к колонкам; одинаковые ситуации решай одинаковыми отступами и размерами. Задай сетку, поля, плотность и шкалу до отрисовки.
- Для нового широкого лендинга допустим исходный вариант: фрейм 1920, контент 1200 по центру, 12 колонок 78 с промежутками 24. Для Tilda — фрейм 1200 с контентом 1160 (или 1920 с сеткой 1200) и отдельный фрейм на блок, подробности — в [профиле Tilda](tilda-ready.md). Для других экранов выбирай сетку по устройству и содержимому.
- Стартовая шкала отступов: 8, 16, 24, 32, 40, 48, 64, 80, 120. Промежутки 4 px допустимы в плотных интерфейсах. Межсекционные 120 и внутренние 24–40 — ориентиры для лендинга, не правило для модального окна или мобильного экрана.
- Стартовые радиусы: поле/кнопка 12, карточка 24, крупная подложка 32–40. В существующем проекте продолжай его значения. Обводки обычно 1–2 px; однотипные иконки — одинаковая сетка и толщина.
- Для обычных неповёрнутых контейнеров, текста и элементов управления используй целые локальные координаты и размеры. Дроби от трансформаций, векторных контуров и распределения auto-layout оценивай по причине; не округляй дерево вслепую. Мировые координаты и кривые не обязаны быть целыми.
- Ключевая информация и действие — в начале и на заметном месте. Сохраняй ясную иерархию; не ставь два одинаково сильных конкурирующих действия рядом без причины сценария.
- Не заполняй пустоту искусственной карточкой. Для нечётного числа элементов используй обоснованную композицию: крупный элемент плюс малые, разную ширину или осмысленный последний ряд.
- Убирай случайные провалы и чрезмерные интервалы, сохраняй полезное свободное пространство. Парные отступы у смены фона или разделителя допустимы.
- Текст и основные действия остаются в контентной сетке. За её пределы могут выходить фото, декор и стрелки карусели, если они не мешают чтению и управлению.
- Фото в одном ряду имеют согласованную высоту. Декоративные наклоны и чередование обычных/асимметричных секций уместны для подходящего лендинга; не переноси их автоматически в формы, таблицы и рабочие экраны. В таком лендинге наклоны фото обычно целые −6…+6°.
- Тени мягкие и согласованы с фоном. Текстуры и декор не ухудшают контраст. Одинаково выглядящие элементы должны иметь понятное одинаковое назначение.
- Не превращай навигационные пункты в один текстовый слой ради экономии слоёв, если им нужны независимые ссылки, состояния или прототипирование. Минимальное число слоёв не важнее редактируемости и функции.
