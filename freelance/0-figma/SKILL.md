# 0-Figma — технический стандарт макетов

Создавай редактируемые макеты в едином стиле: минимум достаточных компонентов, цвета связаны с переменными, типографика — с текстовыми стилями, слои имеют назначение. Применяй стандарт к текущему заданию, не расширяя его до разработки полной дизайн-системы.

## Область и приоритеты

- Указания пользователя и ограничения проекта имеют приоритет. Затем используй существующую дизайн-систему файла; правила ниже — для недостающих решений.
- При совместной работе с `4-landing` используй его для структуры и содержания лендинга, этот скилл — для технического исполнения. Цветовые переменные заменяют требование создавать отдельные цветовые стили; компоненты создавай по необходимости, а не для каждого повторения.
- Не добавляй автоматически «Спасибо», 404, FAQ, мобильную версию, тёмную тему или доску с полным каталогом компонентов. Создавай только то, что нужно для запрошенных экранов.
- Правила типографики и композиции адаптированы из `4-landing`, но этот пакет самодостаточен: читать исходный скилл при каждом запуске не нужно.

## Подготовка

1. Определи файл Figma, целевую страницу/узлы, задачу экрана, размеры и платформу (Tilda, вёрстка, приложение). Бери данные из запроса и существующего файла; спрашивай одним сообщением только о том, без чего невозможно выбрать место или смысл работы.
2. Перед вызовами MCP прочитай актуальный `figma:figma-use`; для видимых изменений — также `figma:figma-generate-design`. При создании переменных, стилей или компонентов прочитай применимые части `figma:figma-generate-library`. Перед созданием нового файла — `figma:figma-create-new-file`. Открывай доступные SKILL.md по каталогу навыков, а не по выдуманному пути. При отсутствии нужного инструмента сообщи об ограничении.
3. Прочитай [основы макета](references/foundations.md) перед первой отрисовкой; [работу через MCP и проверку](references/mcp-and-quality.md) — перед первым чтением или изменением файла через MCP.
4. Проведи разведку: целевые экраны и соседние примеры, доступные библиотеки, компоненты и их свойства, коллекции переменных и режимы, текстовые стили, шрифты. Не обходи весь файл без необходимости.
5. Составь небольшой реестр: какие ID компонентов, переменных и стилей переиспользуешь, чего действительно не хватает. Коротко сообщи пользователю основные решения и продолжай без отдельного согласования, если оно не запрошено.

## Единый стиль и компоненты

- Сначала ищи подходящий существующий элемент по роли, устройству, состояниям и свойствам. Создавай инстанс; не копируй мастер как новый компонент и не отсоединяй инстанс ради удобства.
- Повторение само по себе не требует нового компонента. Компонент нужен для общей структуры/поведения, которое должно правиться централизованно: кнопка, поле, строка, карточка. Простую фигуру, уникальную секцию и целый экран обычно оставляй обычными узлами.
- Перед созданием компонента проверь, решается ли задача свойством TEXT, BOOLEAN, INSTANCE_SWAP или вариантом существующего семейства. Отличие текста или фото не создаёт новое семейство. Не строй все сочетания состояний заранее.
- Новое семейство оправдано другой структурой или поведением, а не другим заголовком. Создавай только реально используемые варианты и необходимые состояния. Удобство редактора и понятность важнее минимального числа любой ценой.
- Новые мастера размещай на существующей доске/странице компонентов проекта; отдельную доску создавай лишь при наличии новых мастеров. Не импортируй библиотеку целиком ради одной кнопки.
- Общие мастера меняй только в рамках задания: изменение затронет все их инстансы. Для локальной особенности используй доступные свойства, а при необходимости — небольшой совместимый вариант.
- Отступы, радиусы, обводки, иконки и принципы выравнивания одинаковы в одинаковых ситуациях. Не создавай почти одинаковые стили ради локальной подгонки.

## Иконки и SVG

- Все интерфейсные иконки, стрелки на кнопках и ссылках, шевроны, крестики, галочки и аналогичные пиктограммы используй в SVG-формате. В Figma они должны оставаться редактируемыми векторными слоями или инстансами векторных компонентов.
- Сначала переиспользуй подходящий векторный компонент из дизайн-системы. Недостающий SVG импортируй через поддерживаемый MCP/Plugin API, например `figma.createNodeFromSvg(svg)`. Повторяющиеся иконки одного назначения используй из одного мастера.
- Не заменяй пиктограммы PNG/JPG/WebP, эмодзи, текстовыми символами стрелок или иконочным шрифтом. SVG с растровой картинкой внутри не считается векторной иконкой.
- Соблюдай единые размеры, толщину обводки и стиль набора; заливки и обводки интерфейсных SVG связывай с цветовыми переменными. Перед сдачей проверь векторную структуру иконок, а не только расширение исходного файла.

## Цвета и текст

- Каждый созданный/изменённый управляемый цвет интерфейса связывай с COLOR-переменной: фоны, текст, иконки, обводки, доступные для привязки цвета теней и стопов градиента. Совпадение RGB с переменной не считается привязкой.
- Переиспользуй существующие переменные по смыслу и режимам. Для нового проекта используй группы `Brand/*`, `Surface/*`, `Text/*`, `Border/*`; создавай роли по мере использования. Подробности и примеры — в foundations.md.
- Цветовые стили не создавай параллельно переменным для каждого цвета. Существующие стили можно сохранить, если их цвета привязаны к переменным. Многослойная заливка может иметь стиль с переменными внутри.
- Растровое изображение, видео, оригинальная многоцветная иллюстрация/логотип не требуют токена для каждого пикселя. Одноцветные интерфейсные SVG и иконки требуют привязки. Недоступную в MCP привязку явно перечисли как исключение.
- Каждому текстовому слою назначай текстовый стиль; в смешанном тексте — каждому диапазону. Цвет текста задавай отдельно переменной. Проверь фактическую типографику: одного непустого `textStyleId` недостаточно при локальных переопределениях.
- Имена новых текстовых стилей: `<Проект>/Display/*`, `Heading/*`, `Numbers/*`, `Body/*`, `Label/*`. При существующей системе сохраняй её названия, а не создавай копии ради своего префикса.

## Слои и очистка

- Удаляй ненужные слои в пределах текущей работы: временные пробы, старые копии, пустые контейнеры без функции и скрытые неиспользуемые элементы. Не оставляй их «на всякий случай».
- `visible=false`, нулевая непрозрачность или выход за границы — повод проверить назначение, а не команда удалить. Сохраняй элементы, нужные для BOOLEAN-свойств, вариантов, инстансов, масок/булевых операций, прототипа, анимации, состояний, адаптива и предусмотренного экспорта.
- В компонентах скрытый необязательный элемент сохраняй, когда он действительно управляется свойством или нужен состоянию; мусор внутри мастера тоже удаляй. Не удаляй дочерние слои инстанса: правь свойства или соответствующий мастер в разрешённой области.
- Не удаляй мастера, переменные, стили и варианты только потому, что они не используются на текущем экране: у них могут быть потребители на других страницах или в библиотеках.
- Перед удалением существующего слоя проверь зависимости и назначение; при неясности оставь его и сообщи причину. Собственные доказанно временные узлы удаляй по их ID.
- Новые слои называй по функции, PascalCase латиницей без служебных номеров: `Header`, `Title`, `Price`, `ProfileCard`. Сохраняй соглашения существующих библиотек и имена вариантов; для Tilda имена и устройство слоёв — по [профилю Tilda](references/tilda-ready.md).

## Сборка и сдача

- Если страница будет на Tilda, прочитай [профиль Tilda](references/tilda-ready.md) до отрисовки и рисуй по нему: секция — отдельный фрейм, у каждой мобильная пара с теми же именами слоёв. Перенос в Tilda делает `5-tilda`.
- Рисуй в указанной области; новую работу размещай на новой странице или свободном участке согласованной страницы. Не меняй соседние работы.
- Подбирай сетку под устройство и продукт. Не применяй 1920/1200, декоративные наклоны или ритм лендинга ко всем экранам. Размеры, типографика и композиционные правила — в foundations.md.
- Сохраняй принятую систему расположения. В новом макете без отдельного указания используй auto-layout для структурно связанных элементов; если пользователь просит без него, расставляй вручную и проверяй размеры текстов/отступы. Не переделывай существующий ручной макет в auto-layout в рамках побочной правки.
- После сборки выполни техническую проверку из mcp-and-quality.md и визуальную проверку скриншотом. Исправь найденное и проверь затронутые места. Скрипт [audit-layout.js](scripts/audit-layout.js) помогает найти проблемы; он только читает узлы и не заменяет проверку композиции, зависимостей и переиспользования.
- Заверши кратко: ссылка на результат; что переиспользовано и создано; привязки цветов и текстовых стилей; что очищено; результат технической/визуальной проверки и оставшиеся исключения. Не объявляй непроверенный пункт пройденным и не выдавай техническую оценку за прогноз конверсии.
