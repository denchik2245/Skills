# Стандарт анализа качественных данных (интервью и ЮТ)

Этот скилл фиксирует единый процесс отдела для перевода сырых интервью и юзабилити-тестов
в структурированную таблицу выводов. Цель — чтобы разные исследователи кодировали данные
сопоставимо, а выводы можно было быстро перепроверить по записи.

---

## 1. Структура таблицы

Единица анализа — **ответ конкретного респондента на конкретный вопрос/гипотезу**, а не
транскрипт целиком. Таблица строится как матрица:

- **Столбцы** — респонденты (один респондент = один столбец).
- **Строки** — сначала блок метаданных респондента, затем содержательные вопросы (для интервью)
  или гипотезы (для юзабилити-теста).

### Блок метаданных (всегда первым, до содержательных вопросов)

Для интервью: роль, сегмент, ОКВЭД/отрасль, дата интервью, ссылка на транскрипт, профиль
респондента (свободный текст), структура отдела/команды респондента.

Для юзабилити-теста: имя, должность, сегмент/ОКВЭД (если применимо), дата теста,
**результат** (успешно/не успешно выполнил задание) и **отдельно** субъективная оценка
сложности сценария самим респондентом — это два разных слоя данных, их нельзя сливать
в одну ячейку.

Если исследование делит респондентов на группы по значимому для гипотезы признаку
(например, «есть продукт-конкурент в обиходе» / «нет»), используй для этого отдельные листы,
а не дополнительный столбец-метку — так группы сразу читаются отдельно.

---

## 2. Маркеры для содержательных вопросов (интервью)

Используются **только текстовые подписи в начале содержательного блока**, не эмодзи —
эмодзи в разных версиях Excel/Google Sheets рендерятся непредсказуемо и плохо ищутся.

| Маркер | Когда ставить |
|---|---|
| **Наблюдение:** | Нейтральный факт по теме вопроса, без признаков проблемы или нерешённости. |
| **Боль/рутина:** | Респондент описывает что-то трудозатратное, повторяющееся или мешающее работе — **даже если не произносит слов «раздражает»/«бесит»**. Критерий — содержание ситуации (требует переделки, лишнего времени, ручного труда), а не наличие эмоциональной оценки в речи. |
| **Без ответа:** | Респондент **не дал содержательного ответа по существу вопроса** (ушёл от темы, отшутился, не понял вопрос). Не путать с «Боль/рутина» — там содержательный ответ есть, просто без явной эмоции. |
| **Не обсуждалось:** | Тема не поднималась на интервью вообще (например, не успели задать вопрос). |

Правило по пустым ячейкам: **пустая ячейка запрещена**. Если темы не было — пиши
«Не обсуждалось:», иначе при сведении по строкам нельзя отличить «не спросили» от
«спросили, но инсайта нет».

Внутри каждого содержательного вывода — отдельный блок **«Цитаты:»** или
**«Опорные фрагменты из транскрипта:»** с таймкодом в формате `чч:мм:сс` перед каждой
цитатой. Любой вывод, помеченный «Боль/рутина» или содержащий спорную трактовку,
**обязан** иметь минимум одну цитату с таймкодом — без таймкода вывод не готов к публикации,
его нужно либо дополнить (вернуться к записи), либо не включать в финальную версию.

Маркер 💭 (рефлексия/догадка исследователя, а не прямое высказывание респондента) и 📃
(тема не обсуждалась подробно) заменяются текстовыми подписями по той же логике, но
важнее всего разделять факт и интерпретацию — см. раздел 4.

## 3. Вердикты по гипотезам (юзабилити-тестирование)

Для каждой пары «гипотеза × респондент» ставится один из четырёх маркеров:

- ✅ **Подтверждена** — пользователь прошёл сценарий так, как предполагала гипотеза,
  без посторонней помощи.
- ✅ **Подтверждена, но...** — то же самое, но с оговоркой/нюансом; трактовка ясна,
  просто не идеальна (например, потребовалась минимальная подсказка, не меняющая суть).
- ❌ **Не подтверждена** — гипотеза была проверена и не подтвердилась: пользователь
  не справился, понял механику неправильно, или потребовалась содержательная помощь
  фасилитатора, чтобы продвинуться дальше.
- 🔵 **Не проверена** — гипотезу не удалось протестировать (респондент не дошёл до этого
  шага сценария, вопрос не задали, технический сбой). Это сигнал нехватки данных,
  а не суждение о поведении пользователя — **не путать с ❌**.
- 🟡 **Вывод спорный** — данные есть, но они неоднозначны, противоречивы (например, на словах
  респондент подтвердил гипотезу, а по действиям — нет), или сам исследователь не уверен
  в трактовке. Любая ячейка с 🟡 **обязательно** выносится на обсуждение в команде
  (см. раздел 6) до того, как таблица станет финальной.

Граница ❌ vs 🔵 — самое частое место ошибок: ❌ ставится только если гипотеза реально
была проверена на этом респонденте и провалилась; если шаг сценария вообще не случился —
это 🔵, иначе при подсчёте процента подтверждения по отделу непроверенные случаи будут
ошибочно занижать показатель.

---

## 4. Факт vs интерпретация

Каждый вывод должен явно разделять то, что респондент сказал/сделал, и то, что
исследователь из этого заключил. Нельзя писать вывод вида «респондент явно боится X»,
если респондент дословно сказал лишь «не уверен, что это поможет» — такая формулировка
смешивает факт с догадкой без пометки об уровне уверенности.

Если нужно зафиксировать интерпретацию исследователя (а не прямое высказывание) —
помечай её явно, например через вводную фразу «Похоже, что...» / «Интерпретация:» —
и не ставь рядом цитату, которая этого не подтверждает напрямую.

---

## 5. Конфиденциальность (PII)

Полные имена респондентов и ссылки на записи звонков допустимы **только** в рабочем
файле с ограниченным доступом внутри команды исследователей. Перед тем как делиться
выводами за пределами команды (презентация продуктовой команде, рассылка шире
отдела) — обезличить: заменить имя на «Респондент N», убрать прямые ссылки на записи.

---

## 6. Расхождения между исследователями

Если несколько исследователей кодируют разных респондентов по одной и той же таблице
вопросов/гипотез, перед началом кодирования **обязательна калибровочная сессия**:
сверить на 2–3 общих примерах, как трактовать пограничные ситуации (например, что считать
«растерянностью», а что — «спокойным обдумыванием» при паузе). Без этого шага один и тот же
тип поведения пользователя у разных исследователей будет попадать в противоположные выводы,
и сравнение по строкам станет ненадёжным. Калибровка повторяется, если по ходу кодирования
всплывает новый пограничный случай, не покрытый предыдущей сверкой.

---

## 7. Версионирование и финализация

Файл не считается финальным только потому, что в нём что-то написано. Прежде чем выводы
уходят за пределы отдела (презентация, отчёт, рассылка продуктовой команде):

1. Таблица проходит проверку **вторым исследователем** (не автором конкретной ячейки) —
   минимум выборочно по ячейкам с 🟡 и ❌.
2. Все «Не обсуждалось:» и пустые ячейки закрыты или осознанно объяснены.
3. Только после этого файл переименовывается из «черновик/промежуточный/копия» в финальную
   версию. Переименование — это **следствие** прохождения проверки, а не способ её заменить.

---

## 8. Чек-лист перед публикацией таблицы

```
СТРУКТУРА
□ Респонденты — столбцы, вопросы/гипотезы — строки
□ Блок метаданных респондента заполнен и стоит первым
□ Для ЮТ: объективный результат и субъективная оценка разнесены по разным строкам

МАРКЕРЫ
□ Нет пустых содержательных ячеек — везде маркер или «Не обсуждалось:»
□ Использованы только текстовые подписи (Наблюдение / Боль-рутина / Без ответа / Не обсуждалось)
□ Для гипотез — только ✅ / ✅...но / ❌ / 🔵 / 🟡, без смешения с эмодзи интервью
□ Нет случаев ❌ там, где гипотеза по факту не была проверена (должно быть 🔵)

ЦИТАТЫ
□ У каждого вывода «Боль/рутина», ❌ и 🟡 есть минимум одна цитата с таймкодом чч:мм:сс

ИНТЕРПРЕТАЦИЯ
□ Догадки исследователя отделены от прямых высказываний респондента

КОНФИДЕНЦИАЛЬНОСТЬ
□ Если файл выходит за пределы команды — имена и ссылки на записи обезличены

ФИНАЛИЗАЦИЯ
□ Ячейки с 🟡 обсуждены в команде
□ Таблицу проверил второй исследователь
□ Файл переименован из черновика только после проверки
```
